## 一、本周我自己改出来的问题

### 1. `renderCharts` 可见性拦截写错顺序 → 整页图表空白

**场景**：D06MBIR1 修完「微前端切走切回图表变形」后，图表全空了。

**错误写法**：

```js
renderCharts() {
  this.disposeCharts();          // 先把已有图表全销毁
  if (!el || !el.clientWidth) {  // 再判断容器可见性
    return;                      // 宽度为 0 就直接返回 —— 销毁了却没重画
  }
  ...
}
```

**正确做法**：判断放在**任何破坏性操作之前**；或者干脆"只跳过 resize、不跳过绘制"。

```js
renderCharts() {
  if (!el || !el.clientWidth) { /* 想清楚这里要不要 return */ }
  this.disposeCharts();          // 走到这一步才允许销毁
  ...
}
```

**教训**：`dispose` / `clear` / `reset` / 重建这类**有副作用的操作，必须放在确认要执行之后**。写在判断前，就等于把"检查不通过"变成了"清空"。

### 2. ve-table 改造第一版的几个欠考虑写法

| 我最初写的 | 导致的症状 | 正确做法 |
|---|---|---|
| 用 `keynum += 1` 重建整表来刷新单元格显示 | 时间面板"滚一格就消失"（面板属于 picker 组件，被一起销毁） | 单元格内容做成**响应式子组件**，绝不用重建整表刷新 |
| 触发元素 `width:0;height:0` | 面板能弹出，但滚轮无效、拖不动滚动条、点一下就关 | 用 `opacity:0` 的**真实尺寸覆盖层** |
| 没注意 `clearable` 默认 `true` | 透明层里点得到看不见的 × 按钮 → 值被清空、面板打不开 | `clearable={false}` |
| 角标放在 flex 流内 | picker 被 focus 后撑开容器，角标被挤走且不恢复 | 角标**绝对定位**，容器不参与布局流 |

**细节与完整清单**：`.claude/knowledge/ve-table-and-list.md` 第 6 节（坑）、第 7 节（标准模板，照抄即可）。

**教训**：用第三方组件做**非默认用法**（把控件藏起来、改变它的尺寸模型）时，先想清楚"它内部依赖什么"——ECharts 依赖容器有尺寸、element-ui 面板依赖触发元素的矩形、ve-table 依赖 `tableData` 的引用。破坏这些前提就会出怪现象。

## 二、这一周最典型的返工：日期问题在四个地方各犯一遍

**现象**：D05M10B1 连着修了 4 轮日期，每轮都像新问题：

1. 列表视图日期差一天
2. 编辑弹窗「日历日期」回显差一天
3. 编辑弹窗「星期」显示为空
4. 日历格子里的内容与表头星期错位

**根因只有一个**：后端返回的是**带时区的 ISO 串**（`2025-12-31T16:00:00.000Z` 其实是北京时间 **次日** 00:00），而前端四个地方各写各的处理方式：

```js
String(x).substring(0, 10)                         // ✗ 差一天
new Date(String(x).replace(/-/g, "/"))             // ✗ 变成非法格式 → Invalid Date → 返回空
this.$options.filters.dateFormats(x)               // ✓ 内部是 new Date(x)，按本地时区还原
```

**教训**：同一个数据在同一个项目里被**四种写法**处理过，说明没人统一过口径。我每次只修用户报的那一处，直到第四轮才回头找共性——**应该在第二次出现时就停下来 grep 全项目**。

**避免办法**：

1. 改任何日期显示前，先 `grep -rn "<字段名>" src/` 看这个字段在项目里还有几处、都用什么方式解析
2. 统一走既有的工具函数（本项目 `src/utils/tools.js` 的 `dateFormats` 就是对的），**不要在页面里各写各的**
3. 遇到"日期差一天"，**先怀疑时区，不要先怀疑数据**

## 三、动手前的检查清单

### 改代码前

- [ ] 这个问题的**同类写法**在别处有没有？先 grep，一次改全（别等用户报第二次）
- [ ] 要用的**表名 / 字段名 / 组件名**，去实际代码或数据库核对——**不信文档、不信直觉**
      （本周 3 处表名文档写错：`Qms_Eightd`→`Qms_EightD`、`Qms_Spc`→`Qms_SpcPoint/Sample`、`SourceType`→`sourcetype`）
- [ ] 有没有现成的工具函数 / 组件能复用（`utils/tools.js`、`@/components`）？不要重复造

### 写"刷新 / 同步"逻辑时

- [ ] 破坏性操作（dispose / clear / 重建）**必须在确认要做之后**执行
- [ ] 数据变了 UI 怎么更新：**优先响应式子组件**，不要重建整表 / 整组件
- [ ] 重建会不会销毁用户正在交互的东西（打开的面板、输入框焦点、滚动位置）？

### 验证时

- [ ] 编译 / 构建通过 ≠ 能跑。**有交互的改动尽量实跑一遍**（本周排程原型就是用浏览器实跑确认的）
- [ ] 修完自查：**这次改动会不会让原本正常的部分坏掉？**（第 3 条那个 bug 就是这么来的）

### 汇报时

- [ ] **自己改出来的问题，直说是"我上一轮改坏的"**，不要混在"历史问题"里带过

## 四、给未来 Claude 的元规则

1. **同一现象第 3 次出现时，停止逐个修，回头找共同根因**——第 2 次就应该警觉
2. **没有视觉反馈时，不要凭直觉改 UI 细节**（宽度、间距、对齐）。这类改动要么保守，要么明确标注"待实测"
3. **用户给的现象描述可能不精确**（"周三显示在周一和周二之间"）。先复述自己的理解、给出判断依据，再动手；判断错了好及时纠正
4. **不确定就查，不要猜**。本周凡是"我猜……"的地方，后面几乎都返工了；凡是"我去库里/代码里查了"的地方，都一次过

5. **技术文档读完，要转成"本次配置清单"逐项核对，不能凭业务直觉删配置**

   本周实例：ve-table 那份文档（当时第 1 条）明确写了 `virtual-scroll-option` 与高度为 0 的关系，**我读了、也看到了**，但判断"这张表只有 7 行，不需要虚拟滚动"，就把它从配置里省掉了 —— 结果整表空白。

   两个偏差叠在一起：
   - **把"业务上不需要"当成了"技术上可以不配"**。那个开关同时控制着容器高度的计算方式，不是纯性能选项。
   - **文档那句话是"现象警告"（会高度为 0），不是"强制指令"（必须开 X）**。读警告时容易想成"那是别人踩的坑/那种模式下才有的问题"，而不是"我这份代码里必须有这一行"。

   所以读技术文档的正确姿势是：**读完立刻列一张"本次要用到的配置项/前置条件"清单，写代码时逐项打勾**，而不是"看过了，心里有数"。

   > 配套改动：该文档的第 1 条已从"警告"改写为"必须开 + 原因 + 案例"；第 7 节末尾有「落地检查清单」，写这类表格时直接照单核对。
