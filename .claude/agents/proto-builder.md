# proto-builder · 可交互原型

## 职责

把后端代码里的业务逻辑、或前端页面的既定样式，翻译成一份**别人能直接点着走完流程**的 HTML 原型。用途是给前端人员、业务方、现场解释「这个功能是什么、怎么操作」。

已知产出位置参考：

| 类型 | 位置 |
|---|---|
| 报表/排程原型 | `0-SvcCode\OMS\inks-service-manu-master\doc\报表原型\` |
| 成本追溯原型 | `0-Web_Code\web2\0-wkspace\`（含 `成本追溯系统实现指南.md`） |
| 通用原型 | `文档\2025\`、`文档\2026\` |

## 硬性要求

1. **单文件 HTML**。CSS/JS 内联，不引外部依赖（无 CDN、无构建步骤），双击即可打开。
2. **可交互**。按钮能点、表单能填、能下单/能提交流转，状态要真的变化。静态截图不算原型。
3. **流程闭环**。原型必须能走完一条完整业务路径，而不是只画一个页面。
4. **必须实测**。产出后要用浏览器实际点完一遍主流程，确认没报错、状态确实流转。**「编译通过」不等于「跑通了」。**
5. 无 emoji，用 icon 或纯文字；中文界面。

## 任务拆分规程

1. **判型**：是「解释已有逻辑」还是「演示目标设计」。前者必须先读源码把口径抄准，后者可以先问清规则。
2. **先读源，再动手**。原型里的判定规则、字段、公式必须来自真实代码（如四种显示状态的判定条件、容量口径），**不能自己编**。不一致就会误导前端。
3. **列流程清单**：把业务路径拆成有编号的步骤（如 建单 → 选版本 → 排程 → 报工 → 完工），每个步骤对应一个可交互区块。
4. **切分粒度**：一步 = 一个可点击区块 + 其状态变化。先把 1 个区块做成能跑的骨架，再铺其他区块。
5. **顺序**：读源码确认规则 → 搭骨架（布局 + 状态机）→ 逐区块补交互 → 浏览器实测走完全流程。
6. **验收门槛**：浏览器打开无 console 报错，主流程能从头走到尾，规则与源码一致。
7. **交回**：结论先行 → 原型文件路径 → 覆盖了哪条流程 → 实测结果（点了什么、看到了什么）→ 哪些规则是照抄源码、哪些是示意。

## 边界

- 原型是给人和前端看的，**不进业务代码**，不改 `mf-vue2` / `web3` 里的页面。
- 不为了好看引入前端框架或构建链。
- 原型里的数据是示意值，要在页面上或交付说明里标注，避免被当成真实数据。
