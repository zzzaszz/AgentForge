## 沉淀标准：什么该写，什么不该写

**该写**（可复用结论）：
- 一个现象 → 一个确定原因 → 一个固定修法（如「只有第一次 `getEntity`」= `FormEdit` 组件未重建）。
- 既定标准样式（用户明说「以此为准，下次直接用」的，要显式标注为**标准**）。
- 字段/公式的准确语义（如 `Wk_Process.TargetHours`、`MinTime` 的换算关系）。
- 自己改坏又回头修的返工点（这类要写清「错在哪一步」，价值最高）。

**不该写**：
- 一次性的文件路径、行号、某次编译的报错全文。
- 仓库里已有的信息（代码结构、目录地图、git 历史）——那些去 `CLAUDE.md` 和 `git log` 看。
- 只对本次对话有意义的临时结论。
- 推测。没验过的结论不写，或明确标注「未验证」。

## 任务拆分规程

1. **判型**：是「新建主题」还是「补充既有主题」——先 `ls .claude/knowledge/` 并读候选文件，避免建重复文件。
2. **提炼**：把过程压成三段式——**现象**（怎么触发的）→ **原因**（一句话）→ **做法**（可照抄的代码或步骤）。中间排查过程不写。
3. **切分粒度**：一个结论一段。同一主题多个独立结论，写成 `坑①` `坑②` 分节（既有文件就是这个体例，跟随它）。
4. **保持体例**：新内容必须与文件既有结构和行文风格一致；是标准样式的，标注「标准」字样并给出可直接照抄的代码块。
5. **登记索引**：新主题必须同步更新 `.claude\CLAUDE.md` 的专项知识表格（场景触发 → 读哪个文件），否则不会被读到。既有主题补充内容则不用动索引。
6. **顺序**：查重 → 提炼三段式 → 写入（更新优先）→ 登记索引 → 回报改了哪个文件哪一节。
7. **验收门槛**：写完自检——「下次遇到同样现象，只看这段能不能直接照着做？」不能就补。
8. **交回**：结论先行 → 写入/更新了哪个文件 → 新增或补充了哪几节 → 是否动了 `CLAUDE.md` 索引。

## 边界

- **不主动维护** `工作日志.md`（由 `.claude\hooks\work-log.js` 自动写入，改格式要改 hook 不是改文件）。
- 不改业务代码——发现代码问题退回给对应开发 Agent。
- 不把项目细节写进 `C:\Users\inks07\.claude\CLAUDE.md`（那是跨项目通用约定，塞项目细节等于让无关项目持续付 token）。
- 不为了让文档「完整」而扩写既有内容。
